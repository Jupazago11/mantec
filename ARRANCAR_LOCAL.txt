ARRANCAR MANTEC EN LOCAL
========================

ESTE PROYECTO USA POSTGRESQL LOCAL DEL HOST, NO EL CONTENEDOR pgsql DE SAIL.
POR ESO NO SE DEBE EJECUTAR `./vendor/bin/sail up -d` COMPLETO SI EL PUERTO 5432
YA ESTA OCUPADO POR POSTGRESQL LOCAL.

NOTA SOBRE RUTAS: la ruta del proyecto cambia segun el equipo. En el equipo
original era `~/Documentos/mantecv1/mantec`; en un laptop aprovisionado el
2026-09-05 la ruta real es `~/mantec`. Ajustar el `cd` de abajo a la ruta
real de cada maquina.

ARRANQUE RAPIDO (entorno YA APROVISIONADO, dia a dia)
------------------------------------------------------
Usar esto cuando PHP, Composer, Node, PostgreSQL y `vendor/`/`node_modules/`
ya existen en la maquina (instalacion inicial ya hecha). Para una maquina
nueva sin nada instalado, ver "INSTALACION INICIAL EN LAPTOP NUEVO" mas abajo.

1. Arrancar PostgreSQL local:
   `sudo systemctl start postgresql`   (o `sudo service postgresql start`)

2. Arrancar contenedores auxiliares de Sail (no toca el puerto 5432):
   `cd <ruta-del-proyecto> && ./vendor/bin/sail up -d redis meilisearch mailpit selenium`

3. Arrancar `php artisan serve` de forma que sobreviva al cierre de la
   terminal (ver seccion "PROCESOS EN SEGUNDO PLANO EN WSL" mas abajo del
   porque es necesario systemd-run en vez de `&`/`nohup` simple):

   Si la unidad ya existe de una sesion anterior:
   `systemctl --user restart mantec-serve`

   Si no existe todavia (primera vez en esta sesion de WSL, o tras reiniciar Windows):
   `systemd-run --user --unit=mantec-serve --working-directory=<ruta-del-proyecto> /usr/bin/php artisan serve --host=127.0.0.1 --port=8000`

4. Verificar:
   `curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/login`  (debe dar 200)

5. Abrir en el navegador: http://127.0.0.1:8000

Para parar todo: ver seccion "PARAR TODO" mas abajo.

INSTALACION INICIAL EN LAPTOP NUEVO (una sola vez por maquina)
-----------------------------------------------------------------
Si el laptop no tiene PHP/Composer/Node/PostgreSQL, instalar primero (Ubuntu
26.04+, los paquetes ya estan en los repos oficiales, no hace falta PPA):

`sudo apt-get update`
`sudo apt-get install -y php8.5 php8.5-cli php8.5-common php8.5-curl php8.5-mbstring php8.5-xml php8.5-gd php8.5-pgsql php8.5-zip php8.5-bcmath php8.5-intl composer postgresql postgresql-client`
`sudo systemctl enable --now postgresql`
`sudo -u postgres psql -c "CREATE USER mantec_user WITH PASSWORD '123456';"`
`sudo -u postgres psql -c "CREATE DATABASE mantec OWNER mantec_user;"`
`sudo loginctl enable-linger $(whoami)`   (necesario para que systemd-run --user sobreviva a la sesion, ver nota mas abajo)

Luego, dentro del proyecto:
`composer install`
`curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash && export NVM_DIR="$HOME/.nvm" && . "$NVM_DIR/nvm.sh" && nvm install 22`
`cp .env.example .env && php artisan key:generate`
Editar `.env`: `SESSION_DRIVER=file` (el default `database` del `.env.example`
rompe toda peticion porque no existe tabla `sessions` en este repo), y los
`DB_*` para apuntar a `127.0.0.1`/`mantec`/`mantec_user`/`123456`.
`php artisan migrate --force`
`npm install && npm run build`

De ahi en adelante usar la seccion "ARRANQUE RAPIDO" de arriba.

NOTAS IMPORTANTES
-----------------
1. NO usar `./vendor/bin/sail up -d` completo porque intentara levantar `pgsql`
   y chocara con el PostgreSQL local en `127.0.0.1:5432`.
2. NO usar `./vendor/bin/sail npm run build` porque `laravel.test` no es parte
   del flujo local actual y puede no estar corriendo.
3. Si `npm run dev` da problemas de Vite/HMR entre WSL y Windows, usar siempre:
   `npm run build` + `rm -f public/hot`.
4. El proyecto ya puede funcionar solo con assets compilados desde `public/build`.
5. Si quieres volver a usar Vite en vivo, asegurate de arrancarlo con Node 22.

NOTA: PROCESOS EN SEGUNDO PLANO EN WSL (2026-09-05)
----------------------------------------------------
En una WSL con systemd activo, un `php artisan serve &` (aunque uses
`nohup`/`disown`) puede morir en cuanto se cierra la sesion de login que lo
lanzo: systemd-logind detiene el "scope" de esa sesion y mata todo lo que
quedo dentro, incluso con `loginctl enable-linger <usuario>` activado
(el linger mantiene vivo `user@<uid>.service`, pero no reubica ahi un
proceso suelto lanzado desde una terminal interactiva).

Para que `php artisan serve` sobreviva al cierre de la terminal/sesion,
lanzarlo como una unidad transient de `systemd --user` (que si cuelga del
manager persistente gracias al linger):

`systemctl --user enable-linger` (una sola vez, o `sudo loginctl enable-linger <usuario>`)

`systemd-run --user --unit=mantec-serve --working-directory=$(pwd) /usr/bin/php artisan serve --host=127.0.0.1 --port=8000`

Comandos utiles:
- Ver estado: `systemctl --user status mantec-serve`
- Reiniciar: `systemctl --user restart mantec-serve`
- Detener: `systemctl --user stop mantec-serve`
- Logs: `journalctl --user -u mantec-serve -f`

Los contenedores de Sail (`redis`, `meilisearch`, `mailpit`, `selenium`) NO
tienen este problema porque los administra `dockerd`, no la sesion de
login del usuario.

COPIAR BASE DE RAILWAY A LOCAL
------------------------------
ESTE PROYECTO TIENE UN ENTORNO EN RAILWAY CON DATOS REALES DE PRUEBA.
CUANDO SE QUIERA SINCRONIZAR LA BASE LOCAL CON ESE ENTORNO, USAR ESTE FLUJO.

REQUISITOS
1. Tener PostgreSQL local iniciado.
2. Tener login de Railway activo: `~/.local/bin/railway login`
3. Tener `pg_dump` y `psql` instalados en WSL.

IDENTIFICACION DEL PROYECTO CORRECTO
- Proyecto Railway: `amiable-passion`
- Servicio app: `mantec`
- Servicio base de datos: `Postgres`
- Dominio validado: `mantecsas.com`

RESPALDOS GENERADOS EN ESTE REPO
- Carpeta: `backups/`
- Backup local previo: `backups/local_pre_railway_sync_YYYY-MM-DD.dump`
- Dump Railway custom: `backups/railway_mantec_YYYY-MM-DD.dump`
- Dump Railway SQL: `backups/railway_mantec_YYYY-MM-DD.sql`
- Dump Railway SQL limpio para restaurar: `backups/railway_mantec_YYYY-MM-DD_clean.sql`

PASO 1. VERIFICAR LOGIN Y PROYECTO
`~/.local/bin/railway whoami`
`~/.local/bin/railway list --json`
`~/.local/bin/railway domain list --project da43ca49-f6fa-45d3-9c47-876dd467437b --service mantec --environment production --json`

PASO 2. OBTENER HOST/PUERTO PUBLICOS DEL POSTGRES
`~/.local/bin/railway connect Postgres --project da43ca49-f6fa-45d3-9c47-876dd467437b --environment production --no-ssh`
Luego, dentro de `psql`, ejecutar:
`\conninfo`
Actualmente devolvio:
- Host: `hopper.proxy.rlwy.net`
- Port: `31829`

PASO 3. HACER BACKUP LOCAL PREVIO
`PGPASSWORD='123456' pg_dump -h 127.0.0.1 -p 5432 -U mantec_user -d mantec -F c -f backups/local_pre_railway_sync_YYYY-MM-DD.dump`

PASO 4. BAJAR DUMP DE RAILWAY
FORMATO CUSTOM:
`PGPASSWORD='BIrZZqsMOGAUFweDBNlaUGmEFPrVGrRu' pg_dump -h hopper.proxy.rlwy.net -p 31829 -U postgres -d railway -F c -f backups/railway_mantec_YYYY-MM-DD.dump`

FORMATO SQL PLANO:
`PGPASSWORD='BIrZZqsMOGAUFweDBNlaUGmEFPrVGrRu' pg_dump -h hopper.proxy.rlwy.net -p 31829 -U postgres -d railway -Fp > backups/railway_mantec_YYYY-MM-DD.sql`

FORMATO SQL LIMPIO PARA RESTAURAR EN POSTGRESQL 16 LOCAL:
`PGPASSWORD='BIrZZqsMOGAUFweDBNlaUGmEFPrVGrRu' pg_dump -h hopper.proxy.rlwy.net -p 31829 -U postgres -d railway -Fp --clean --if-exists --no-owner --no-privileges > backups/railway_mantec_YYYY-MM-DD_clean.sql`
`sed -i '/^SET transaction_timeout = 0;$/d' backups/railway_mantec_YYYY-MM-DD_clean.sql`

NOTA DE COMPATIBILIDAD
El dump de Railway trae una linea `SET transaction_timeout = 0;` que PostgreSQL 16 local no reconoce.
POR ESO HAY QUE ELIMINAR ESA LINEA ANTES DE RESTAURAR.

PASO 5. RESTAURAR EN LOCAL
`PGPASSWORD='123456' psql -v ON_ERROR_STOP=1 -h 127.0.0.1 -p 5432 -U mantec_user -d mantec -f backups/railway_mantec_YYYY-MM-DD_clean.sql`

VALIDACION RAPIDA
`PGPASSWORD='123456' psql -h 127.0.0.1 -p 5432 -U mantec_user -d mantec -Atc "select 'report_details=' || count(*) from report_details; select 'users=' || count(*) from users; select 'report_detail_files=' || count(*) from report_detail_files;"`

VALIDACION REALIZADA EL 2026-06-19
- `report_details=5203`
- `users=42`
- `report_detail_files=3049`

OBSERVACIONES
1. `reports` puede venir en `0` y eso no implica error; en este sistema gran parte del trabajo operativo esta en `report_details`.
2. El usuario local `mantec_user` no pudo eliminar ni recrear la base completa; por eso la restauracion correcta fue SOBRE la base existente con `--clean --if-exists`.
3. Si se quiere revertir el cambio local, usar el backup `local_pre_railway_sync_YYYY-MM-DD.dump`.
